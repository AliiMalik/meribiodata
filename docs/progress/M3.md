# M3 — Templates & export

**Shipped:** 2026-08-05

Exit criteria: ≥4 templates, the chosen PDF pipeline, all P0+P1 languages rendering correctly,
image export, share sheet, golden tests per template × script. Met, with one caveat recorded
under "Outstanding" — the P1 label translations are drafts, not reviewed.

## What shipped

**A render-ready document model.** `DocumentBuilder` turns a stored profile into a
`RenderedDocument`: hidden fields and sections filtered out, labels resolved, values formatted
(dates with their display mode, height in ft/in or cm, weight, currency, sibling shorthand),
digits converted, and bidi isolation applied. Templates never see a profile, a schema or a label
resolver — which is what lets them render *whatever schema exists* (§6.4).

**One layout, two backends.** Templates emit a `DocBlock` list — the layout IR the M0 report
called for. `BlockWidgets` interprets it as Flutter widgets (Pipeline B) and `PdfRenderer`
interprets it as `pdf` widgets (Pipeline A). `ExportService` routes by script per D1, so no
caller ever picks a pipeline: choosing wrongly is precisely the failure M0 exists to prevent.

**Four templates.** Classic (default), Print Shop (fully monochrome, heavier rules — many users
print black and white at a corner shop), Elegant (roomier, gold accent), Compact (for long
biodatas). Each is layout, typography and ornament only.

**Pagination.** Pipeline B rasterizes a fixed-size page and so cannot use `pw.MultiPage`. The
exporter lays the document out once off-screen, measures every block, and `Paginator` splits it
into page slices — never inside a block, never stranding a section heading at the foot of a page,
and splitting oversized blocks rather than looping. The §6.3 sixty-field case is covered by test.

**Export.** PDF (vector for Latin, raster otherwise), one JPEG per page for images, and the
system share sheet. Exports land in a dedicated directory so NFR-7's "delete all my data" can
clear them. **No ad banner on this screen**, per §8.

**Template picker and export screen.** The picker's thumbnails are the real renderer at small
scale rather than shipped images, so a template cannot look different in the picker from how it
exports. The export screen previews through the same widgets, which is what will make 9.4's
"preview must render the actual selected mode" true rather than approximate.

**Golden tests.** 20 goldens: four templates × English, Urdu, Sindhi and Pashto, plus an empty
document, a 60-character label, the 4×6 card, and Shareable mode. Regenerate with
`flutter test --update-goldens`.

## Verified on device

Pixel emulator, API 36. Created a biodata, previewed it, exported English PDF (8 KB, vector) and
Urdu PDF (80 KB, raster) — the size ratio M0 predicted — then exported a JPEG and pulled it back
to confirm the Urdu Nastaliq, the RTL layout and the watermark all survive the off-screen capture.

## What surprised me

- **Noto Naskh Arabic ships no glyphs for `/ ( ) - +`.** Every phone number, every date, every
  parenthesised age needs them, and Sindhi and Pashto use Naskh as their *primary* font. Their
  fallback chain was empty, so those characters would have been supplied by whatever font the
  device happened to have — the same device-dependent rendering the UI font chain fixed in M1,
  in the one place it matters most. Found by inspecting the font files' `cmap` directly rather
  than by rendering and squinting, which is now a permanent test.

- **The goldens caught what the unit tests could not.** Every formatting test passed while an
  Urdu biodata still said "31 years", "5 ft 9 in" and "1 married" in English, because the
  document's own vocabulary was hardcoded. It is now in the same data asset as the labels, keyed
  by document language.

- **The bidi fix works, and it is visible.** `+92 300 1234567` renders correctly in the Urdu
  golden and in the on-device export. That was the single concrete defect M0 found.

- **The export screen was unreachable.** Every screen was routed and tested, and there was still
  no button anywhere that opened it. Tests that mount a screen directly will never catch this;
  only driving the real app did.

- **`kotlin.incremental` had to be turned off.** Plugin builds failed with "Could not close
  incremental caches", survived `flutter clean`, and survived killing the daemons. Disabling
  incremental Kotlin compilation costs a few seconds per build; a build that fails half the time
  costs much more.

## Outstanding

- **Sindhi, Pashto and Punjabi document labels are drafts.** They render correctly and are marked
  `draft` in `_reviewStatus` in the labels asset, and the export screen shows a notice when the
  selected language is unreviewed. They still need a native reviewer before launch — open
  question 1 in `docs/decisions.md`. Until then, "all P0+P1 languages render correctly" is true
  of the *rendering* and not yet of the *wording*.

- **Still no low-end device timing.** Export time is not yet benchmarked against NFR-2 on real
  hardware. The emulator is comfortably fast, which tells us little; M0's DPI/time curve stands
  as the guide and the default is 200 dpi for images, 300 for print PDFs.

- **The watermark text is a placeholder** — "Made with MeriBiodata". Open question 8.

- **Share was not exercised end to end**: the emulator has no WhatsApp, so the share sheet opens
  but nothing receives the file. The 9.1 round-trip test belongs to M5 anyway.

- **`DocumentStrings` for P2 languages** fall back to English. Fine for now — P2 is post-launch.

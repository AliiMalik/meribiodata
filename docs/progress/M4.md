# M4 — Monetization & waitlist

**Shipped:** 2026-08-05

Exit criteria: AdMob adaptive banner + UMP consent, airplane-mode acceptance test passes, waitlist
screen. All met and verified on device.

## What shipped

**App identity.** `applicationId`, `namespace` and the Kotlin package are now
`safarnamastudios.meribiodata.app` (D9). This is the last milestone in which that could change for
free — the id is immutable once published to Play.

**Ad configuration.** `AdConfig` defaults to Google's official test unit IDs and takes the real one
from `--dart-define=ADMOB_BANNER_UNIT_ID=…`. The AdMob **App ID** cannot come from a Dart define
because it lives in the manifest, so it is a Gradle manifest placeholder defaulting to the test App
ID and overridden with `-PadmobAppId=…`. Nothing real is committed, and CI now fails if it ever is.

**Consent before ads.** `ConsentGate` runs the UMP flow and only then initialises the Mobile Ads
SDK. Every failure path — offline, no Play services, a form that will not load, an SDK that will
not start — lands on "no ads". The ordering is tested explicitly, because initialising first and
asking afterwards still *works*, which is exactly what makes it an easy mistake to ship.

**Banner slot.** Anchored adaptive, bottom only, on Home and the Form Editor. Placement is an
allowlist (`AdConfig.bannerScreens`), not a denylist, so a screen added later gets no ad by
default — the safe direction for that list to fail. It occupies reserved layout space rather than
overlaying anything, and collapses to zero height when there is no consent, no fill or no network.

**Waitlist.** Opens a hosted form in the user's browser (D8). The screen states what the form asks
for and where it goes *above* the button, not after it, and a test asserts that ordering. Handles a
successful launch, no browser, and a launch that throws, each with a visible message.

**CI.** The NFR-1 guard now names the two permitted network callers, and two new guards were added:
one rejecting in-app webviews in `lib/` (D8 — `webview_flutter` arrives transitively via the ads
SDK, so the check is on our own use of it), and one rejecting any committed AdMob ID that is not a
Google test ID.

## Verified on device

Pixel emulator, API 36.

| Case | Result |
|---|---|
| Consent runs before ads initialise | `UserMessagingPlatform` resolves (`gdprApplies:0`), then the ads SDK starts. No crash. |
| Banner on Home | Requests 426×133, loads, renders in reserved space with content clear above it. |
| Banner on the Form Editor | Loads; the form scrolls above it and no field is covered. |
| **No banner on Preview & Export** | No slot rendered and no request logged. The policy-critical case. |
| **Airplane mode** | Consent fails cleanly ("disabling ads"), no crash, slot collapses to zero height with no blank strip, app fully usable. |
| Waitlist offline | Screen renders with both disclosures; no ad slot. |

## What surprised me

- **`getLargeAnchoredAdaptiveBannerAdSize` returns null on this device, and my first version
  returned silently when it did.** The slot collapsed with no ad and no log line — on a device that
  is indistinguishable from "ads are switched off", and I only noticed because I expected a test ad
  and did not get one. It now falls back to a standard banner and logs every decision point. A
  silent early return in a widget whose *correct* behaviour is also "render nothing" is a genuinely
  bad combination.

- **Adding the banner changed tap targets in an existing screen.** The Home empty-state button moved
  up by the banner's height, which broke my own scripted device taps. Harmless here, but it is the
  concrete form of the §8 warning about ads and layout — anything positioned by absolute
  coordinates, including a user's muscle memory, shifts when an ad loads.

- **`google_mobile_ads` pulls in `webview_flutter` transitively.** Ads render in a webview, so the
  dependency is unavoidable — which means "no webviews" cannot be enforced at the lockfile level.
  The CI guard checks `lib/` for our own imports instead, which is the honest version of that rule.

- **The consent SDK reports failure through a callback, not an exception.** `requestConsentInfoUpdate`
  takes success and failure callbacks; wrapping it in a `Completer` and *completing with an error* on
  the failure path is what lets the gate's single `try` see it at all.

## Outstanding

- **The waitlist form URL is a placeholder.** A test asserts it still is, so the day a real URL
  lands, that test fails and prompts its own update. Supply it via
  `--dart-define=WAITLIST_FORM_URL=…` or edit the constant.

- **No real AdMob account**, so only test ads have ever rendered. Real IDs are a build-flag change;
  a real banner has never been observed loading.

- **UMP was only exercised outside the EEA.** `gdprApplies` came back 0, so the consent *form* never
  actually displayed. The EEA path — where a form appears and the user can refuse — is covered by
  unit tests but has not been seen on a device. Worth an emulator with an EEA locale before launch.

- **NFR-5 privacy policy and Play Data Safety** still to be drafted in M5. This milestone settled
  what they have to say: the AdMob SDK collects advertising data, and the waitlist hands name,
  WhatsApp number and city to a Google Form — both disclosed separately from the "biodata never
  leaves your device" claim.

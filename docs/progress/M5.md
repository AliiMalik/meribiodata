# M5 — Differentiators

**Shipped:** 2026-08-06

Exit criteria: 9.1 WhatsApp-first export, 9.2 Roman Urdu input, 9.3 photo handling, 9.4 Full vs
Shareable modes, 9.5 encrypted backup. All five built, 319 tests green, verified on device.

## What shipped

**9.4 — Full vs Shareable (`fac462a`).** Two named modes rather than a per-field checklist:
*Wide sharing* and *One family*. The screen opens in Shareable **every time** and resets to it
whenever it is reopened (D11). The preview is built in the selected mode, so what is on screen is
the document, and a live count says how many details are hidden or shortened. Masking is
`omit`, `generalise` or `placeholder` per field: a date of birth becomes an age, an address becomes
its last line.

**9.1 — WhatsApp-first export (`30a17d1`).** A third co-equal button beside Export PDF and Save
image. `share_plus` cannot target one app, so this is an `ACTION_SEND` with the package set,
through a FileProvider scoped to the exports directory alone. Falls back to the ordinary share
sheet when WhatsApp is absent — the button reads "Share" then — because on a phone without it the
user still expects the button to do something.

**9.5 — Encrypted `.mbd` backup (`e662c96`).** AES-256-GCM with an Argon2id-derived key, a
plaintext header the restore screen reads before asking for anything, and a `MERIBDTA` magic
number. Wrong password and tampering are indistinguishable, which is the property that makes
tampering detectable at all. Restore offers Merge or Replace, and Replace confirms twice. The
device key from NFR-6 is deliberately *not* reused: this file leaves the phone.

**9.2 — Roman Urdu input (`4381062`, `385ea8b`).** A rule engine plus a 288-word dictionary, fully
on-device. Per-field toggle with a candidate strip, defaulting from a setting.

**9.3 — Photo handling (`23fdac9`).** Pick from gallery or camera, frame in a fixed portrait crop,
rotate, store on the device only. The metadata requirement is not implemented as a strip step: the
picked file is decoded to pixels, drawn onto a fresh canvas and re-encoded, so EXIF and GPS have no
path through. `ExifScanner` *checks* that, in tests and in a debug assertion. Photos are opt-in per
export and the choice resets on every mode change (D12); they live in `photos/`, outside the only
directory the FileProvider can grant from; and they travel inside the encrypted backup.

**Platform bridge (`2d1499b`).** `file_picker` had to go — its Android build still evaluates the
removed `jcenter()`, and every version that fixes that pins a `win32` range `share_plus` rejects.
Replaced by ~40 lines of Storage Access Framework in `MainActivity.kt`, folded into the WhatsApp
channel and renamed `.../platform`.

## What surprised me

- **`flutter_image_compress`'s `minWidth`/`minHeight` are a bounding box, not a floor.** I passed
  `1, 1` to mean "do not resize this, it is already the size I want", wrote a comment saying so, and
  got a **760-byte, one-pixel photograph**. Every unit test passed, because they all stub the
  platform encoder — the one step no test could reach was the one that was wrong. The encoder now
  receives the size the image already has, and a test asserts that it does.

- **The metadata assertion fired on the app's own clean output.** Android's JPEG encoder attaches an
  ICC colour profile in APP2, and my first scanner flagged all of APP1–APP15. The fix is narrow:
  APP2 is excused only when the payload carries the `ICC_PROFILE` signature, so FlashPix — which
  shares the marker — stays flagged. Worth noting that the assertion working *is* the good outcome
  here: it caught real encoder behaviour no fixture had modelled.

- **A crash in an M2 helper that M5 merely exposed.** `promptForText` disposed its
  `TextEditingController` in `whenComplete`, which fires when `Navigator.pop` is called — while the
  route is still on screen animating out. Harmless for eighteen months of single dialogs; the backup
  screen pushed a second dialog in that same frame and it surfaced as
  `'_dependents.isEmpty': is not true`, an inherited-widget assertion with nothing in the stack
  pointing at the cause. Fixed at the source by giving the dialog a `State` that owns the controller.

- **The two chained password prompts were the wrong design anyway.** Replacing them with one dialog
  holding both fields removed the crash *and* improved the flow: the no-recovery warning is now
  visible while the user chooses, and a mismatch no longer means retyping both entries.

- **The ad banner is a hazard for scripted testing, exactly as §8 warns for users.** One mistimed
  tap during a device run landed on the AdMob test banner and opened a browser. The M4 note about
  ads shifting layout has a second half: they also occupy a place a finger was about to go.

- **A `.mbd` has no registered MIME type**, so the SAF picker must be opened with `*/*`. Anything
  narrower makes the user's own backup unselectable, and the file's magic number rejects a wrong
  pick immediately anyway.

## Transliteration accuracy, measured honestly

Two numbers, because only one of them means anything:

| Set | Result |
|---|---|
| In-dictionary (195 words) | **100.0%** (195/195) |
| **Held-out (20 words, rules only)** | **45.0%** (9/20) |

The first is close to meaningless — the evaluation words are drawn from the same dictionary the
engine looks them up in. It exists only as a regression floor. The second is the number that
predicts what a user sees when they type a name the dictionary has never met.

The misses cluster into recognisable groups: `-war`/`-awar` endings (*Zorawar*, *Dilawar*,
*Bakhtawar*), doubled consonants at a morpheme boundary (*Mehrunnisa*, *Naimatullah*), and long `aa`
in a final syllable (*Barkat*, *Nusrat*). Each is a rule, not a dictionary entry, so the honest next
step is rules — adding these eleven words to the dictionary would raise the first number and change
nothing about the second.

## Outstanding

- **Not tested with WhatsApp actually installed.** The emulator has none, so only the fallback path
  has ever run. The intent, the package targeting and the FileProvider grant are unit-tested, but no
  message has been observed arriving.

- **The camera path was not exercised on device** — only gallery. The emulator's camera is a
  synthetic scene and the flow is the same after `pickImage` returns, but that is an argument, not a
  test.

- **Restore was verified with photos already present.** `PhotoStore.writeAt` demonstrably rewrote
  the file (mtime changed), but the "photos directory is empty, restore recreates it" case has only
  been covered by unit tests, which do run it against a genuinely empty temporary directory.

- **No backup password strength policy** beyond a minimum of 8 characters (open question 7). Argon2id
  makes a weak password expensive to attack but not safe; this is still a decision to take.

- **The 3 GB reference device has still never run this.** Everything here was measured on an
  emulator. NFR-2 (< 3 s export) and the memory behaviour of a 12 MP photo decode remain unverified
  where they matter.

- **`docs/decisions.md` open questions 1, 2, 3, 5, 8 remain open**, unchanged from M4. Question 6
  (photos: default or opt-in) is closed by D12.

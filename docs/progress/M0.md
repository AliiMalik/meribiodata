# M0 — Nastaliq PDF spike

**Shipped:** 2026-08-04

## What shipped

- `spike/nastaliq_spike/` — throwaway Android-only Flutter app rendering one biodata-shaped
  document through all three candidate pipelines in Urdu, Sindhi, Pashto and English.
- `docs/spike-nastaliq.md` — the spike report: outputs, numbers, recommendation, fallback plan.
- `docs/spike-assets/` — curated page renders referenced by the report.
- Noto Nastaliq Urdu + Noto Naskh Arabic (SIL OFL) vendored with license text.

**Recommendation: hybrid — Pipeline B (raster) for Perso-Arabic, Pipeline A (vector) for Latin.**
Awaiting sign-off before M1 architecture work starts.

## Deferred

## What surprised me

- **Pipeline A is worse than "poor".** The build prompt predicted Nastaliq quality would be
  "poor to unacceptable"; the actual output is unreadable — collapsed glyph piles, tofu, `MBBS`
  rendered as `SBBM`, `15 مارچ 1995` rendered as `19959915`. There is no tuning path from here.
  Usefully, the same pipeline is excellent for Latin, which is what makes the hybrid worth doing.

- **Pipeline C failed for reasons that have nothing to do with typography.** `Printing.convertHtml`
  is deprecated, the Android plugin never reports the capability (so `canConvertHtml` is always
  `false`), and `PrintingJob.convertHtml()` sets its `WebViewClient` *after* starting the page
  load, so the completion callback can never fire and the future hangs. Rendering the same HTML
  through Blink directly showed correct shaping and real embedded vector fonts — the idea is
  sound, the library path is not.

- **The phone-number bug is a spec problem, not a bug.** `+92 300 1234567` reverses to
  `1234567 300 92+` in every RTL pipeline including Blink, because that is correct Unicode bidi.
  It needs isolate marks (`U+2066`/`U+2069`) applied per field type in the field engine — which
  means it is an M2 data-model concern, not an M3 template concern.

- **My own capture harness was silently wrong the first time.** `SizedBox` enforces incoming
  constraints, so the page laid out at 190×269 pt and was upscaled to A4. The output looked like
  a rendering failure rather than a harness failure. The production capture path carries an
  explicit boundary-size assertion because of this.

- **Cost is PNG encoding, not rasterization.** Time scales linearly with pixel count
  (327 ms @150 dpi → 1319 ms @300 dpi, warm). That reframes the NFR-2 fix as "encode JPEG
  natively" rather than anything architectural.
